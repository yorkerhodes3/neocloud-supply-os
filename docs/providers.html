Risk provider kit

One risk interface. Any provider.

The design never assumes a third-party risk provider. Every document says RISK_PROVIDER, and every desk calls one of eleven canonical capabilities. A registry in code maps each capability to the configured provider's own MCP tool or API call, and tags every name with how we know it. Add ?risk= to any link to dress a demo for the provider in the room.

02 · Capability matrix

Canonical capability → native call.

What each desk would actually call, per provider. A ~ marks a canonical name standing in where the provider publishes none. A gap names the fallback the registry uses, so the demo never pretends a capability exists.

03 · Signal mapping

Their categories, our signals.

Each provider's own factor ids or event types map onto ten internal signals (concept D3), and the policy engine acts on the signal, never on the vendor's label. Empty cells are gaps that official lists or a second source must fill.

04 · Analysis

Do providers share function names? Partly.

The hypothesis was that MCP-enabled risk providers expose similarly named functions. The evidence supports it for verbs, not for strings, and only two of the four providers publish names at all.

    05 · Dress and extend

    Any name in the slot, any provider in the registry.

    White-label the generic provider

    Shows the canonical interface under any name, for example a prospect's in-house risk platform. Names and tools stay canonical, so nothing is claimed about a real product.

    Add a provider

    1. Copy the generiq entry in docs/assets/js/providers.js and give it a new key.
    2. Fill tools with native names from public docs and tag each basis: documented, reference, announced or none. Mark gaps with a fallback.
    3. Map the provider's categories to the ten signals in factors.
    4. Add its id to PROVIDER_ORDER. Run npm test: the registry tests check every entry is complete and honest.
